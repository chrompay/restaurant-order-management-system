# Full-Stack Integration Spec: restaurant-admin ↔ restaurant-api

This document is the living reference for the project to connect every page of `restaurant-admin` to real data in `restaurant-api`/MongoDB, expanding the backend where needed. It complements `CLAUDE.md` (architecture/conventions) — this file tracks the **plan, API contracts, and decisions** for the integration project specifically, and is updated as each phase actually lands (deviations from the original plan are noted inline, not silently absorbed).

Status key: `[ ]` not started · `[~]` in progress · `[x]` done (with any notes on what actually shipped vs. planned).

## Why this project

`restaurant-admin` was originally a Figma "Make" export: every page under `src/app/pages/` renders from local `MOCK_*` constants. Only the auth feature (`src/features/auth/`) is genuinely wired to `restaurant-api`. This project replaces every mock data source with a real API call, backed by MongoDB, expanding `restaurant-api` with the net-new domains (dashboard, analytics, customers, kitchen, delivery/riders, settings) it doesn't support yet — while preserving the existing frontend visual design.

## Decisions locked in

- **Roles**: `User.role` enum expands from `["customer","admin"]` to `["customer","admin","manager","staff","kitchen","delivery"]`.
- **Admin-created orders**: must reference an existing registered customer — no guest/walk-in order support.
- **Kitchen station**: real field. `Food.station` (enum `["Grill","Fryer","Expo"]`), snapshotted onto `Order.items[].station` at order-creation time (same convention as `foodName`/`priceAtPurchase`).
- **Notifications**: the header bell stays mocked/deferred this round — no `Notification` model.
- **Delivery**: full `Rider` model, live location fields, Leaflet + OpenStreetMap map (no paid API key). Order-destination pins are out of scope for v1 (no geocoding infra) — rider markers only.
- **Foods images**: real upload via `multer`, local disk storage under `restaurant-api/uploads/`, served via `express.static`. `Food.image` stays a plain string URL path (no cloud storage this round).
- **Settings**: full scope — restaurant profile + business hours, real "My Account", full team/role management, notification *preferences* (distinct from the deferred live feed), password change. Appearance and 2FA stay client-only/decorative.
- **Currency**: Nigerian Naira (₦), not USD. Shared formatter at `src/lib/currency.ts` (`formatCurrency(amount)`, backed by `Intl.NumberFormat('en-NG', {style:'currency', currency:'NGN'})`) — use this in every phase touching a price/amount display, don't hand-roll `$${x.toFixed(2)}` again. Applied retroactively to Foods and Orders (Phase 2/3); still-mocked pages (Dashboard, Kitchen, Delivery, Customers, Analytics, Settings) will pick it up naturally as each is rewired.

### Known temporary state
- **`config/rateLimiter.js`'s global limiter is disabled** (`app.use(apiLimiter)` commented out in `server.js`) at the user's explicit request, after a frontend refetch-loop bug (see Phase 3) exhausted the 100req/15min limit and locked out the entire API for 15 minutes at a time during dev. **Must be re-enabled before any real deployment** — it's currently the only thing standing between this API and unlimited request volume from any client.

### Smaller defaults (adjustable later, not worth their own review round)
- VIP/Regular/New: VIP = `totalSpent >= 100000 OR totalOrders >= 20`; New = `totalOrders <= 1`; else Regular. (Updated in Phase 7 — originally `>= 500`, a stale USD-scale number left over from before the Naira currency switch.)
- `Order.discountAmount` (default 0) added so Analytics' "Discounts & Refunds" KPI is real, not faked.
- `Order.items[].notes: String` (optional) added for real Kitchen ticket notes.
- Kitchen "target prep time": hardcoded constant through Phase 8; as of Phase 9, read live from `RestaurantSettings.targetPrepTimeMinutes`.
- `RestaurantSettings` / `NotificationPreference` are find-or-create-on-first-GET documents (no seed migration).
- Team "Invite Member": admin directly creates the account with a role (adapts `registerUser`) — no email-invite infra.
- Filename casing fix (`foodcontroller.js` → `foodController.js` etc.): via `git mv`, per `CLAUDE.md`'s stated preference.

### Implementation gotchas found during planning (verified against actual code, not assumed)
- `authorize(...roles)` (`middleware/roleMiddleware.js`) already accepts multiple roles variadically — no middleware change needed for later phases' multi-role gating.
- `protect` (`middleware/authMiddleware.js`) re-fetches the user fresh from MongoDB on every request (`User.findById(decoded.id)`), not from the JWT payload — a role change takes effect on the user's very next request, not after token expiry.
- **Multer must run before Joi `validate`** in any route chain that accepts file uploads (`protect, authorize, upload.single(...), validate(...), controller`) — `validateMiddleware.js` checks `req.body`, which for multipart requests is only populated once multer parses the stream. Wrong order = spurious validation failures.
- Multer's `diskStorage` does not create missing destination folders — ensure `restaurant-api/uploads/foods/` (etc.) exists at startup via `fs.mkdirSync(..., {recursive:true})`.
- The shared frontend axios instance (`src/services/api/axios.ts`) hardcodes `Content-Type: application/json`. Any request sending a `FormData` body must override/remove that header per-call so the browser sets the correct `multipart/form-data` boundary — otherwise the file silently never arrives.

### Phase 2 — Foods & Categories (Menu Management)
Goal: real CRUD, real image upload, real search/filter/pagination; Categories show real item counts/revenue.

**New/changed backend:**
- `middleware/uploadMiddleware.js` (new): multer disk storage → `restaurant-api/uploads/foods/`, image-type filter (jpeg/png/webp), ~2MB limit, destination dir auto-created at startup.
- `middleware/parseJsonFields.js` (new, not in original plan text but required by it): multipart fields are always strings, and a repeated field name only becomes an array in `req.body` when sent 2+ times (single-value case silently stays a scalar). Since `Food.ingredients` needs to reliably be an array regardless of item count, the frontend sends it as a single JSON-stringified field and this middleware parses it back before Joi/Mongoose see it. Wired as `upload.single("image") → parseJsonFields(["ingredients"]) → validate(schema)`.
- `POST /api/foods`, `PATCH /api/foods/:id`: gain `upload.single("image")` + `parseJsonFields` ahead of `validate`.
- `validators/foodValidator.js`: new `updateFoodSchema` (all fields optional, min 1); both schemas gained optional `availability`/`station`.
- `foodController.js`: `createFood`/`updateFood` set `req.body.image` from `req.file` when present; `updateFood`'s 404 now uses `AppError` (was raw `res.json`); `getFoods` gained a `?menu=` (category) filter.
- `models/Menu.js` fields added: `icon` (String, default `"utensils-crossed"`), `status` (enum `["Active","Draft"]`, default `"Active"`).
- `models/Food.js` field added: `station` (enum `["Grill","Fryer","Expo"]`, default `"Grill"`).
- `GET /api/menus`: paginated, plus per-menu `itemCount`/`revenue` aggregation (single grouped aggregation each, not N+1 per-menu queries). Revenue is attributed via each order item's food → food's *current* menu (order items don't snapshot menu, only foodName/price), expressed as a % share of total revenue, rounded to 1 decimal.
- `server.js`: `app.use("/uploads", express.static("uploads"))`.
- `middleware/errorMiddleware.js`: added a `MulterError` case (400, matching the existing special-cased-error-type convention) — without it, a rejected upload (bad file type, too large) would 500 instead of a clean 400.
- Ran `npm audit fix` after adding multer (unrelated transitive `brace-expansion` DoS advisory, fixed non-breaking).

**Frontend:**
- `src/features/foods/`, `src/features/categories/` (feature-folder pattern per `src/features/auth/` template): types, zod schemas, `api/*.api.ts`, React Query hooks (`useFoods`/`useCreateFood`/`useUpdateFood`/`useDeleteFood`/`useUpdateFoodAvailability`, `useCategories`/`useCreateCategory`/`useUpdateCategory`/`useDeleteCategory`), `FoodForm`/`FoodTable`/`FoodCard`/`CategoryForm` components.
- `src/app/pages/Foods.tsx`, `src/app/pages/Categories.tsx` fully rewired off mock data, including search (debounced via new shared `src/hooks/useDebouncedValue.ts`), category filter, pagination, and working create/edit/delete/availability-toggle flows. Categories' "Manage Items"/"View Items" now link to `/menu/foods?menu=<id>`, which Foods reads via `useSearchParams` to pre-filter (kept in sync via a `useEffect` so repeated in-page navigation between categories updates the filter, not just first mount).
- **Deviation from mock design**: dropped the mock's "Cost" and "Stock" columns/fields entirely — the real `Food` model has no wholesale-cost or inventory-count concept (`availability` is a boolean toggle, not a quantity), and the approved Phase 2 backend plan didn't add them. Inventing fake numbers for these would have reintroduced the exact static-data problem this project exists to remove.
- **Deviation from CLAUDE.md's UI-kit-by-directory rule**: `src/features/foods/components/*` and `src/features/categories/components/*` import from `src/app/components/ui` (the kit `src/app/pages/*` uses) rather than `src/components/ui` (the smaller kit `src/features/auth/*` uses). Reasoning: unlike the auth feature's standalone `LoginPage`, these components render embedded directly inside `src/app/pages/Foods.tsx`/`Categories.tsx` alongside other `src/app/components/ui` elements (Card, Tabs, Pagination, Dialog) on the same page — using the smaller kit would risk visible visual inconsistency (e.g. a differently-styled Table/Switch) on a single page, which cuts against "the frontend design should remain."
- Confirmed empirically (not assumed) that the shared axios instance's default `Content-Type: application/json` silently corrupts `FormData` uploads: axios's `transformRequest` `JSON.stringify`s the FormData (losing the file) whenever a JSON content-type is already set. Fix: `food.api.ts`'s multipart calls explicitly pass `headers: { "Content-Type": undefined }` so axios/the browser can set the correct multipart boundary. Confirmed via a throwaway local HTTP server test — this exact axios version (1.18.1) reproduces the corruption without the override and works correctly with it. The same override will be needed for Phase 9's avatar upload.
- Form numeric fields (`price`, `preparationTime`) use plain `z.number()` + `register(field, { valueAsNumber: true })` rather than `z.coerce.number()` — the latter created an input/output type mismatch between zod and `@hookform/resolvers/zod` that `tsc` caught (coerce's pre-transform type is `unknown`, conflicting with `useForm<FoodFormValues>`'s expected field types).
- Mounted `<Toaster />` (from `src/app/components/ui/sonner`) in `App.tsx` — `sonner` was a dependency but never actually rendered anywhere, so `toast()` calls used by the new mutation hooks would have silently done nothing.
- Removed `src/services/food.service.ts`/`menu.service.ts` placeholders (replaced by the feature folders).

Verified: `GET /api/menus` returns real aggregated `itemCount`/`revenue` against live data; `tsc --noEmit` clean (only pre-existing unrelated errors in `calendar.tsx`/`main.tsx` remain); Vite transforms both rewired pages without error. Admin-gated write paths (create/update/delete food & category, image upload) were not exercised end-to-end by me — no admin credentials available in this session; user will verify these manually in-browser.

**Bug found during user testing, fixed same phase**: `src/app/components/ui/textarea.tsx` (and the same copy at `src/components/ui/textarea.tsx`) was a plain function component, not wrapped in `React.forwardRef` — unlike `input.tsx`, which does this correctly. On React 18 (this project's version), a `ref` passed to a non-forwardRef function component is silently dropped. `react-hook-form`'s `register()` relies on that ref to read an uncontrolled field's live DOM value at submit time; without it, the field resolves to `undefined` regardless of what the user typed, which zod then reported as "Invalid input: expected string, received undefined" on the Description field. This is a latent bug in the original Figma-exported kit — nothing before this phase paired `Textarea` with `register()`. Fixed both copies with `React.forwardRef`, matching `Input`'s pattern.

### Phase 3 — Orders (Operations)
Goal: full live order list/detail/status/create; admin create-order restricted to existing customers.

**New/changed backend:**
- `models/Order.js`: `items[]` gained `station` (enum, snapshotted from `Food.station`) and `notes` (optional string) — `items[].completed` still deferred to Phase 5 as planned.
- `GET /api/orders/all-orders`: adds customer search (`?search=`, regex on `fullName`/`email`, resolved to `customer: {$in: [...]}`) and `createdAt` date-range filter (`?from=&to=`). Order-ID substring search was **not** added — real orders only have Mongo ObjectIds (no human-friendly sequence number like the mock's "#1049"), so a raw hex-string search box wouldn't be meaningful; search is customer-only, matching the approved plan's stated scope.
- `GET /api/orders/my-orders`: added pagination (parity fix, was unpaginated).
- `POST /api/orders`: accepts optional `customerId` — only honored when `req.user.role === "admin"` and the id resolves to a real `User` (404 otherwise); snapshots `station` (from the food) and `notes` (from the request item) onto each order line.
- Both order queries' customer populate extended from `"fullName email"` to `"fullName email phone address"` — needed for the order detail view's real Customer Details card (these fields exist on `User` since Phase 1).
- `validators/orderValidator.js`: `createOrderSchema` gained optional `customerId` and per-item optional `notes`.

**Frontend:**
- `src/features/orders/` (types incl. `OrderStatus`/`ORDER_STATUSES`, zod schema, `api/order.api.ts`, `useOrders`/`useCreateOrder`/`useUpdateOrderStatus` hooks, `lib/orderDisplay.ts` for status colors/short ID formatting, `lib/printReceipt.ts`). `src/app/pages/Orders.tsx` fully rewired: real search/status/date-range filtering, table + kanban views (kanban groups the same query client-side, no separate endpoint), real pagination, order detail sheet with a working status-update `Select`, and a working Create Order dialog.
- **Deviation from mock**: dropped the `priority` ("High"/"Normal") field and the fabricated "Tax & Fees: $5.00" line in the order summary — neither has a real backing field on `Order`, and inventing them would reintroduce fake data. The kanban card's "prep time" is now real elapsed-time-since-`createdAt`, not a canned string.
- **CreateOrderDialog's customer picker is a raw account-ID text input**, not a search — exactly the interim state the approved plan anticipated ("restrict to searching by email/id directly"), since no `GET /api/users` lookup endpoint exists until Phase 7. It's explicitly labeled as temporary in the UI and will be replaced with `useCustomers()` once Phase 7 lands.
- `lib/exportCsv.ts` added at the shared `src/lib/` level (not orders-specific) since it's a generic CSV-from-rows utility.
- `printOrderReceipt` opens a formatted print window with real line items/total (no fabricated tax line), using `window.print()` — no new dependency needed.

Verified: `tsc --noEmit` shows no new errors; Vite transforms all new files; `GET /api/orders/all-orders` with the new `search`/`status`/`from`/`to` query params returns 401 (not a 500) when unauthenticated, confirming the new filter logic doesn't crash. Admin-gated flows (create order, status update) not exercised end-to-end by me — no admin credentials this session.

**Bug found during user testing, fixed same phase**: `Orders.tsx` called `getDateRange(dateFilter)` directly in the render body. For the "Today"/"Last 7 Days" presets, that function calls `new Date()` internally — so every render produced a brand-new `to` ISO timestamp, which fed into `useOrders`'s React Query key (`["orders", params]`). A changing key on every render triggers a refetch on every render, which triggers a re-render, forever. At the observed ~2 requests/second this exhausted the API's 100-req/15-min rate limiter within roughly a minute, after which *every* request on *every* page started failing with 429 — the likely real cause of the "Failed to load orders" screenshot. Fixed by wrapping the call in `useMemo(() => getDateRange(dateFilter), [dateFilter])` so the range is only recomputed when the filter selection actually changes.

**Process hygiene note**: while chasing this, `TaskStop` on the backend dev-server task didn't actually kill the underlying `node`/`nodemon` process tree on Windows — repeated restart attempts left up to 13 orphaned `node.exe` processes running (confirmed via each process's full command line), with an old orphan still bound to port 5000 serving stale, rate-limited code well after the fix had landed and the tracked task had supposedly restarted. Resolved by identifying every orphan via `Get-CimInstance Win32_Process` (command line, not just name) and killing all of them before starting one clean instance each of the API and Vite dev servers. Worth checking for orphaned processes (`netstat -ano` + matching PID to command line) if a dev server ever seems to be running "old" code despite a restart.

### Phase 4 — Dashboard (first aggregation phase)
Goal: real KPIs w/ day-over-day deltas, real charts, real kanban/recent-orders/activity feed.

**New/changed backend:**
- `utils/analyticsAggregations.js` (new, shared with Phase 8): `getRevenueTotal`, `getOrderCount`, `getDistinctCustomerCount`, `getRevenueSeriesByHour`, `getOrderVolumeByHour`, `getAvgDeliveryMinutesByHour`, `getTopFoods`, `getOrderStatusCounts`, `getKitchenQueueStats`. All revenue figures exclude `Cancelled` orders.
- `routes/dashboardRoutes.js` + `controllers/dashboardController.js` (admin/manager): `GET /api/dashboard/{kpis,revenue-series,peak-hours,prep-time-series,top-foods}`.
- **Simplification vs. original plan text**: no `/board` or `/recent-orders` endpoints were added — Phase 3's `GET /api/orders/all-orders` already supports `sort`/`limit`, so the Dashboard's kanban board, recent-orders list, and activity feed all just call that existing endpoint with different params (`{limit:100}`, `{limit:5, sort:'-createdAt'}`, `{limit:8, sort:'-updatedAt'}`) instead of duplicating logic in a new endpoint. The activity feed is synthesized from `updatedAt`/`status` exactly as planned (no new model), described as "Order #XXXXXX marked as {status}".
- "Kitchen Queue" KPI = count of `Confirmed`/`Preparing` orders + their average elapsed wait time so far (computed via `$$NOW` in the aggregation, not pulled into Node). "Kitchen Performance" chart = avg minutes from `createdAt` to `updatedAt` on `Delivered` orders, grouped by hour — an honest proxy for "time in the pipeline," not a precise prep-only duration (there's no per-status-transition history to compute that exactly); labeled accordingly in the UI.
- Known simplification: hour buckets (`$hour` in aggregations) are UTC-based, not per-viewer-timezone-aware. Reasonable for a single-timezone restaurant; would need revisiting for multi-timezone deployments.

**Frontend:** `src/features/dashboard/` (types, `api/dashboard.api.ts`, one hook per endpoint, each polling via `refetchInterval` — 30s for KPIs, 60s for charts — so the "Live updates active" indicator is actually true, not just decorative). `src/features/dashboard/lib/fillHours.ts` fills in all 24 hours with 0 for any missing from the aggregation, so charts don't show misleading gaps. `src/app/pages/Dashboard.tsx` fully rewired: KPI cards, live kanban board (reusing Phase 3's `OrderKanban` component directly), revenue/peak-hours/kitchen-performance/top-foods charts, recent orders, and activity timeline. "New Order" now navigates to Orders; "Export" downloads a CSV of today's orders via the existing `exportToCsv` utility. "Pause Online" was dropped (no backing concept exists — would need a new Settings-level online-ordering toggle, out of scope here).

Verified: all 5 new endpoints require auth and don't 500 (confirmed via curl); `tsc --noEmit` clean; Vite transforms the rewired page; no HMR errors across the whole rewrite. Not exercised with real authenticated data by me this session — no admin credentials.

Status: `[x]` done.

### Phase 5 — Kitchen
Goal: real active-order ticket board, persisted item completion, real bump/recall.

**New/changed backend:**
- `models/Order.js`: `items[].completed` (Boolean, default false).
- `PATCH /api/orders/:orderId/items/:itemId/toggle` (admin/manager/kitchen) — finds the item via Mongoose's built-in subdocument `.id()` lookup, flips `completed`, saves.

Purely additive (admin retains access), so no regression risk.
- Bump/recall reuse the existing status endpoint with a computed next/prev status (`src/features/kitchen/lib/statusFlow.ts` on the frontend) — no new status-transition endpoint.

**Frontend:** `src/features/kitchen/` (`lib/statusFlow.ts` for the next/previous linear-status walk, `lib/ticketStatus.ts` for elapsed-minutes/urgency derivation, `hooks/useBumpOrder.ts` — marks any still-incomplete items complete via Phase 3's toggle endpoint, then advances status — and `useRecallOrder.ts` — steps status back one). `src/features/orders/` gained `useToggleOrderItem` (shared, since it operates on the `Order` resource) and `OrderItem.completed`/`_id` on the shared type. `src/app/pages/Kitchen.tsx` fully rewired: tickets are `Confirmed`/`Preparing` orders (fetched via Phase 3's `useOrders`), station tabs now really filter (by `items[].station`, hiding a ticket entirely if none of its items match), elapsed time and urgency (late/warning/normal) are live-computed from `createdAt` every 30s — fixing a latent bug in the original mock, where a `currentTime` tick existed but was never actually used to recompute each ticket's displayed elapsed minutes. "Recall" changed from a fully decorative header button (mock never wired it to anything, not even to undo `bumpTicket`) to a real single-level undo: bumping stores the just-bumped order (its post-bump state, needed to correctly compute one status step back), and Recall reverts it.
- **Deviation from mock**: dropped `type` (Dine-In/Takeout/Delivery), `destination` (Table/Pickup/etc.), and `server` fields — none have a backing concept in this system (every order is a real customer's online order; there's no dine-in/table/server modeling anywhere). Replaced with the real customer name. Per-item `notes` render as a single free-text line (real schema, from Phase 3) rather than the mock's array of structured modifier tags.

Verified: new/changed routes require auth and don't 500 (confirmed via curl); `tsc --noEmit` clean; Vite transforms all new files with no HMR errors.

### Phase 6 — Delivery (full rider tracking)
Goal: real rider fleet, real assignment, live map of rider positions.

**New/changed backend:**
- `models/Rider.js` (new): `name`, `phone`, `vehicleType` (enum `["car","bike","scooter"]`), `status` (enum `["available","en_route","returning","offline"]`, default `available`), `location {lat,lng,updatedAt}`. `routes/riderRoutes.js` + `controllers/riderController.js` + `validators/riderValidator.js`: `GET/POST /api/riders` (list is paginated+status-filterable via the shared `paginate.js`), `PATCH /api/riders/:id`, `PATCH /api/riders/:id/location` (admin-manual stand-in, per the plan — no rider-facing client exists to call this itself yet). Read routes also allow the `delivery` role; writes are admin/manager only.
- `models/Order.js`: `assignedRider` (ref `Rider`, default null). `getAllOrders`/`getMyOrders` now also `.populate("assignedRider", "name phone vehicleType status location")`.
- `PATCH /api/orders/:orderId/assign-rider` (admin/manager, new `assignRiderSchema` in `orderValidator.js`): sets `assignedRider` and forces `status` to `"Out For Delivery"`.
- **Design decision (not spelled out in the original plan, needed to actually build this)**: the order-status enum has no distinct "ready, awaiting driver" state — Kitchen's Bump (Phase 5) already advances `Preparing → Out For Delivery` on its own. So "Waiting for Driver" vs "En Route" isn't two different `status` values; it's the same `"Out For Delivery"` status, split client-side by whether `assignedRider` is set yet. Assigning a rider doesn't introduce a new status, just fills in the ref (status was already `"Out For Delivery"`).
- Added a "Mark Delivered" action (reuses the existing `PATCH /:orderId/status` endpoint, no new route) — without it, en-route orders had no path to `Delivered` at all, since the mock's original en-route card only had decorative "Track"/"Contact" buttons.

**Frontend:** `leaflet` + `react-leaflet@^4` added (**not** the latest react-leaflet v5, which requires React 19 — this project is on React 18.3.1, confirmed via a failed `npm install` before pinning the v4 range) + `@types/leaflet`. `src/features/riders/` (types, schema, api, hooks, `RiderForm`, `RiderManagementDialog` — a single dialog that toggles between a rider list with inline status-change and location-entry, and the create/edit form) and `src/features/delivery/` (`useAssignRider` reusing Phase 3's order API, `AssignDriverDialog`, `FleetMap`). `FleetMap` uses `L.icon()` pointed at the imported marker PNGs — Leaflet's default icon URLs don't resolve under Vite's bundler otherwise, a well-known Leaflet+bundler gotcha. Map defaults to centering on Lagos (no real restaurant address exists yet; that lands in Phase 9) when no rider has a known location.
- **Deviations from mock**: dropped `distance` and `eta`/`on_time`/`delayed` fields (no geocoding/routing exists, matching the "no order-destination pins in v1" decision) and the fabricated "Avg Delivery Time" header stat (would need a new analytics endpoint out of this phase's scope; "Active Drivers X/Y" stayed since it's directly computable from the real rider list). "Track" opens the same fleet map rather than a per-order zoomed view; "Contact" is a real `tel:` link using the assigned rider's phone; "Print Label" reuses Phase 3's `printOrderReceipt`.

Verified: all new/changed endpoints require auth and don't 500 (confirmed via curl); `tsc --noEmit` clean; Vite optimized and transformed the new `leaflet`/`react-leaflet` dependencies with no errors; user's live session (visible in server logs) continued working across the whole rewrite with no crashes.

Status: `[x]` done.

### Phase 7 — Customers

### Post-Phase-10 bug fix — `SheetContent` blank page on Orders detail view

User-reported: creating an order, then clicking it on the Orders page, produced a fully blank page.

**Root cause**: `src/app/components/ui/sheet.tsx`'s `SheetContent` only ever applied fixed-position offset classes (`inset-y-0 left-0 ...`) for `side === "left"`. Every other `side` value — including `"right"`, the component's own default — fell through with no positioning classes at all. `OrderDetailSheet.tsx` (Phase 3) is the only place in the codebase that renders a `Sheet` without explicitly passing `side="left"`, so it was the first real usage to hit this gap (the only other usage, `AppLayout.tsx`'s mobile sidebar, always passes `side="left"` and was unaffected). With no `inset`/`top`/`right` classes, the un-positioned content fell into normal document flow inside its Radix portal (appended to `document.body`, outside `AppLayout`'s `h-screen overflow-hidden` wrapper) — landing just below the 100vh app shell, off-screen. Meanwhile `SheetOverlay` (`fixed inset-0 bg-black/80`) still correctly covered the entire viewport, so the user saw a full-screen dark overlay with no reachable content: exactly "blank page, shows nothing." This was never caught earlier because this project's verification methodology (curl, `tsc --noEmit`, Vite-transform checks) never included actually opening a Sheet/Dialog in a browser.

**Fix**: rewrote `SheetContent` to use `class-variance-authority` (already a dependency, same pattern as `button.tsx`/`badge.tsx`) with proper `top`/`bottom`/`left`/`right` variants, matching the canonical shadcn `sheet.tsx` implementation. The `left` variant's classes are byte-for-byte unchanged from before, so the one working usage (`AppLayout`'s mobile sidebar) is unaffected; `right` (and `top`/`bottom`, unused today but now correct for future use) now get real positioning. Fixed at the shared primitive, not in `OrderDetailSheet`, so any current or future `Sheet` usage anywhere in the app is covered — searched the codebase and confirmed no other page currently uses `Sheet` at all besides these two.

Verified: `tsc --noEmit` and a Vite-transform fetch both clean; traced the actual CSS/DOM mechanics against `AppLayout`'s `h-screen overflow-hidden` shell and Radix's portal-to-`document.body` behavior to confirm the failure mode matches the reported symptom exactly.

- **Login gate (frontend-only)** — `restaurant-admin/src/features/auth/constants.ts` (new) exports `STAFF_ROLES = ["admin", "manager", "kitchen"]`. `delivery` and `staff` are excluded: `delivery` can view riders/update location but can't act on an order's status, and `staff` has no wired capability anywhere (both pre-existing gaps, documented in Phase 10 above) — locking out `admin`/`manager`/`kitchen` would have shelved functionality that already works, so those three stayed. `AuthProvider.tsx`'s `login()` and mount-time `restoreSession()` both check `STAFF_ROLES` — a rejected `login()` throws (surfaced inline by `LoginForm`'s existing catch), a rejected session-restore clears storage and fires a `sonner` toast, so a customer who logged in *before* this change is also kicked out on their next load, not just newly-blocked at the form. `POST /auth/login` itself is unchanged and still open to `customer` role — the future customer app needs that same shared endpoint. Found and fixed in passing: `login()`'s catch block used raw `localStorage.removeItem("token")` instead of `authStorage.clear()`, leaving a stale `auth_user` record on a failed login.
- **Team-invite consistency** — Settings → Team could invite a `delivery`/`staff` teammate (default role was literally `'staff'`, the one role wired to nothing), who'd then be unable to log in at all post-gate. `TEAM_ROLES` restricted to `["admin", "manager", "kitchen"]` in `restaurant-api/validators/userValidator.js` and mirrored in the three frontend spots duplicating it (`settings.schema.ts`, `settings.types.ts`, `Settings.tsx`); invite form default changed to `'kitchen'`.
- **`GET /menus/:id` gap closed** — previously returned only the bare `Menu` doc; a customer app browsing a category would need a second manual `GET /foods?menu=:id` call. `menuController.js`'s `getMenu` now also fetches `Food.find({ menu: id, availability: true })` and returns `{ ...menu, foods }`. Not consumed by `restaurant-admin` today (only `PATCH`/`DELETE /menus/:id` are used there), so purely additive.
- **CORS hardened** — `server.js` previously called `cors()` with no options at all (any origin allowed). Replaced with an explicit allowlist read from a new `CLIENT_ORIGINS` env var (comma-separated), defaulting to `http://localhost:5173` if unset. Adding the future customer app's origin later is just an env var edit, no code change.
- **Confirmed already sufficient, no changes needed**: `POST /auth/register` (defaults to `role: "customer"`), `GET/PATCH /auth/profile`, `PATCH /auth/change-password`, `GET /foods` + `GET /foods/:id` (both public; `Food` schema already has every Food-Details-Module field the requirements doc asks for except optional ratings), `GET /menus`, `POST /orders` (server-calculated `totalAmount`, can't be spoofed by a client), `GET /orders/my-orders`, `PATCH /orders/:orderId/cancel` (ownership-checked). This is the full surface a customer app needs, and none of it required a role beyond a valid login.

**Explicitly not done this pass**: the customer-facing app itself (separate future project); a dedicated `GET /orders/:id` for customers (the existing list + create-order response already return full order objects); the rate limiter (still disabled, per standing prior decision); removing `delivery`/`staff` from the `User.role` enum (kept for when those roles get real capability built, just excluded from dashboard login and team-invite for now).

Verified: `tsc --noEmit` clean; a real browser walkthrough confirmed a customer-role login is rejected at the form with a clear message, admin/manager/kitchen logins are unaffected, and a simulated stale pre-change customer session gets silently signed out on reload rather than rendering a broken dashboard; curl checks confirmed every customer-relevant endpoint still works with a plain customer JWT and that CORS now rejects an unrecognized `Origin` while still allowing `http://localhost:5173`.
